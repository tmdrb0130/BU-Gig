# 백석대학교 긱창업 플랫폼 기능·페이지 명세

> 목적: 실제 개발에 필요한 **페이지, 기능, 사용자 흐름, 상태값, 기본 권한**만 정리한다.  
> 핵심 방향은 `의뢰 게시판`이 아니라 **작업물과 실력을 중심으로 사람을 찾고, 완료 경험이 다시 포트폴리오 경력으로 쌓이는 매칭 플랫폼**이다.
>
> **디자인 기준 최신화: 2026-09-30** — 홈 / 프로젝트 탐색 / 전문가 탐색 시안과 프로젝트 상세 UX 결정을 반영한다.

## 0. v2 적용 기준 및 페이지 연결

2026-09-30 구현 대조 개정. 이 문서의 기능 목록은 목표 범위이며 구현 완료 목록이 아니다. 실제 코드 상태는 [docs 인덱스](README.md), 서버 구조는 [시스템 아키텍처](시스템_아키텍처.md), 상태 전이·API·권한 제안은 [데이터·API 계약](데이터_API_계약.md)을 따른다.

### 현행 프론트와 핵심 누락

홈·프로젝트/전문가/작업물 탐색·각 상세·의뢰 작성·지원 작성·찜은 프론트 동작이 있다. 워크룸·채팅·계약·MY는 예시 데이터 기반 부분 구현이다. 로그인·가입은 브라우저 한정 데모다. 서버 인증·DB·객체 권한·실시간 전달·메일은 없다.

포트폴리오 등록/수정은 **사용자 디자인 대기**로 둔다. 프로필 편집, 지원자 선정, 지정 요청 수신 처리, 프로젝트별 워크룸, 계약 버전/쌍방 동의, 학교 인증, 알림 목록, 완료/후기, 관리자 화면은 추가 작업이다.

### 목표 경로와 접근 기준 — 신규 경로는 설계 제안

| 화면 | 현재 또는 제안 경로 | 목표 접근/주요 행동 |
| --- | --- | --- |
| 로그인/가입/재설정 | 현재 `/login`, `/signup`, `/password-reset` | 비회원, 성공 후 안전한 원래 작업으로 복귀 |
| 학교 인증/온보딩 | 제안 `/verification`, `/onboarding` | 본인 인증 상태·보완·짧은 프로필 작성 |
| 계정 설정 | 제안 `/settings/account`, `/settings/notifications` | 본인, 민감 변경 재인증 |
| 내 프로필 | 제안 `/my/profile/edit` | 본인 수정·미리보기, 공개 프로필 `/experts/:id`와 연결 |
| 포트폴리오 관리 | 제안 `/my/portfolios` | 본인 목록·공개·대표작 관리 |
| 포트폴리오 작성/수정 | 예약 `/works/new`, `/works/:id/edit` | **디자인 대기**, 본인만 접근 |
| 의뢰 수정 | 제안 `/projects/:id/edit` | 소유자 및 수정 가능 상태 |
| 지원자 목록/비교 | 제안 `/projects/:id/proposals` | 의뢰자만, 선정·2~3명 비교 |
| 내 지원 상세 | 제안 `/proposals/:id` | 작성자 및 해당 의뢰자 |
| 지정 요청 | 제안 `/requests/:id`, `/my/requests` | 발신/수신 당사자, 수락·견적·거절 |
| 대화 목록/대화 | 제안 `/messages`, `/messages/:id` | 멤버만, 읽음·파일·관련 의뢰 링크 |
| 프로젝트 워크룸 | 제안 `/workrooms/:id?tab=overview|chat|contract|files` | 매칭 당사자. 현재 `/workroom`은 단일 데모 |
| 계약·버전 | 제안 `/contracts/:id?version=:n` | 당사자, 워크룸 계약 탭에서 진입·이력·문서 |
| 완료/후기 | 제안 워크룸 내 완료 확인, `/projects/:id/review` | 수행자 요청·의뢰자 확인, 완료 거래만 후기 |
| 알림 | 제안 `/notifications` | 수신자별 목록·읽음·대상 링크 |
| 고객센터/문서 | 제안 `/support`, `/support/tickets/:id`, `/terms`, `/privacy` | 공개 안내, 문의는 본인/담당자 |
| 관리자 | 제안 `/admin/*` | 별도 운영 권한·감사, 일반 회원 메뉴와 분리 |

전문가/의뢰자 역할은 페이지별 행동 문맥이지 별도 계정 유형이 아니다. 로그인 route guard는 UX용이며 서버 API도 동일 권한을 검사해야 한다.

### 화면 간 연결과 상태 요구

1. 비회원이 등록/지원/찜을 누르면 로그인 후 허용된 내부 경로로 복귀한다. 이미 입력한 비민감 초안은 사용자 확인 후 복원한다.
2. 게시/지원 전 학교 인증 필요 정책은 운영 승인 대상. 만료된 인증과 기존 계약 이행 권한을 구분한다.
3. 선정 응답의 workroomId로 실제 방에 이동한다. 예시 `/workroom`으로 모든 거래를 보내지 않는다.
4. 계약은 초안/동의 대기/체결본/변경 검토본을 구분하고 최신 버전이 바뀌면 재검토하도록 한다.
5. 소유자 아닌 방문자, 마감, 이미 지원, 삭제/비공개, 401/403/409, 저장/업로드 실패마다 CTA와 설명이 달라야 한다.

### 최신 필터 요구

카테고리/세부 분야는 한 패널, 여러 대분류/세부 항목 OR 선택, 나머지 조건과 AND. 분야 선택 중 패널을 유지하고 적용/취소한다. 예산 직접 입력 지원, 평점은 4.5/4.0/3.5 이상. 토글은 필터 뒤에 같은 간격으로 이어 두며 별도 ‘빠른 조건’ 그룹을 만들지 않는다. 직접 기간·분야별 기술 추천·기술/진행 방식 다중선택은 아직 미구현인 후속 항목이다.

## 1. 서비스 핵심 구조

백석대학교 구성원이 교내에서 필요한 업무·제작·서비스를 의뢰하고, 수행 가능한 구성원이 지원하거나 의뢰자가 전문가/작업물을 직접 찾아 요청하는 플랫폼이다.

### 핵심 매칭 경로

```text
A. 의뢰 등록 → 수행자 지원 → 비교 → 선정
B. 전문가 검색 → 프로필 확인 → 지정 요청
C. 작업물 탐색 → 포트폴리오 확인 → 수행자에게 지정 요청
```

### 매칭 이후

```text
선정
→ 프로젝트 워크룸 생성
→ 메시지/조건 협의
→ 계약
→ 작업 진행
→ 완료 확인
→ 후기
→ 검증 포트폴리오 등록
```

### 플랫폼 내 포함

- 회원가입 / 로그인
- 학교 구성원 인증
- 수행자 프로필
- 경력 / 기술
- 포트폴리오
- 제공 가능한 작업
- 프로젝트 의뢰 등록 / 탐색
- 전문가 탐색
- 포트폴리오 탐색
- 지정 요청
- 지원 / 견적
- 수행자 비교 / 선정
- 프로젝트 워크룸
- 프로젝트 단위 메시지
- 파일 공유
- 계약 작성 / 버전 관리 / 쌍방 동의
- 작업 완료 확인
- 후기
- 완료 작업의 검증 포트폴리오 전환
- 알림
- 찜
- 문의 / 신고 / 분쟁
- 공지 / 배너
- 관리자 기능

### 제외

- 플랫폼 내 결제
- PG
- 에스크로
- 정산 / 환불
- 외부 전자서명 서비스
- 복잡한 크몽식 상품 옵션/패키지
- AI 추천 알고리즘

금전 지급은 당사자 간 직접 처리한다.

플랫폼에는 다음만 기록한다.

- 합의 금액
- 계약 조건
- 계약 동의 기록
- 프로젝트 상태
- 완료 확인 기록

## 2. 사용자

하나의 계정으로 의뢰자와 수행자 기능을 모두 사용한다.

| 사용자 | 주요 기능 |
|---|---|
| 일반 사용자 | 의뢰 등록, 프로젝트 지원, 전문가 탐색, 작업물 탐색, 지정 요청, 메시지, 계약 |
| 수행 활동 사용자 | 프로필, 기술, 경력, 포트폴리오, 제공 가능한 작업, 지원 |
| 학교 인증 사용자 | 학생 / 교수 / 교직원 인증 배지 |
| 관리자 | 회원·인증·프로젝트·계약·문의·신고·콘텐츠 관리 |

별도의 `의뢰자 계정`, `전문가 계정`을 만들지 않는다.

# 7. 프로젝트 등록

프로젝트 등록의 목표는 **의뢰자가 공고를 꾸미는 것**이 아니라, 필요한 정보만 입력하면 시스템이 읽기 쉬운 프로젝트 상세 화면으로 자동 구성되게 하는 것이다.

대표 이미지나 홍보용 배너 제작을 요구하지 않는다. 프로젝트의 본질은 `무슨 일을 / 얼마에 / 언제까지 / 어떤 결과물로` 원하는지 빠르게 전달하는 것이다.

## 7.1 등록 UX 원칙

- 작성 예상 시간: **2~5분**
- 데스크톱 / 모바일 모두 단계형 작성
- 단계마다 필수 항목을 최소화
- `임시저장` 지원
- 이탈 시 저장되지 않은 변경사항 경고
- 마지막 단계에서 `미리보기`
- 상세페이지에서 보이는 순서와 등록 폼의 정보 구조를 최대한 동일하게 유지
- 이미지 업로드는 **선택**
- 같은 내용을 설명란과 별도 필드에 중복 입력시키지 않음

## 7.2 권장 작성 단계

```text
1. 기본 정보
→ 2. 작업 내용
→ 3. 보상·일정
→ 4. 참고자료·확인
→ 등록
```

### 1단계 — 기본 정보

필수:

- 프로젝트 제목
- 대분류 카테고리
- 세부 서비스/분야
- 한 줄 요약

선택:

- 필요한 기술/도구 태그

제목 예:

```text
학과 행사 포스터 디자인
동아리 소개 반응형 웹페이지 제작
축제 스케치 영상 편집
영문 발표자료 교정 및 피드백
```

### 2단계 — 작업 내용

필수:

- 프로젝트 내용
- 원하는 결과물

선택:

- 작업 요청사항
- 참고 스타일 / 참고 링크
- 수정 협의 가능 여부 및 범위

`프로젝트 내용`은 자유 텍스트로 작성하되, 화면에서는 줄바꿈을 유지하여 읽기 쉽게 표시한다.

`원하는 결과물`은 선택형 + 직접 추가를 병행한다.

예:

```text
✓ A2 포스터 1종
✓ SNS 홍보 이미지 1종
✓ 편집 가능한 원본 파일
```

### 3단계 — 보상·일정

필수:

- 예산 유형
  - 고정 금액
  - 범위
  - 협의
- 작업 희망 기간 또는 완료 희망일
- 모집 마감일

선택:

- 희망 시작일
- 진행 방식
  - 온라인
  - 오프라인
  - 혼합
- 오프라인 진행 시 장소/캠퍼스 범위

예산은 상세 화면과 목록 카드에서 가장 중요한 정보 중 하나이므로 숫자 표시 형식을 통일한다.

```text
100,000원
100,000~200,000원
협의
```

### 4단계 — 참고자료·확인

선택:

- 이미지
- PDF
- 문서
- 압축파일
- 외부 링크

파일은 `파일명 / 형식 / 용량`을 표시한다.

대표 이미지는 별도 필수 필드로 두지 않는다.

프로젝트 카드에 썸네일이 필요한 경우 우선순위:

```text
1. 첨부된 이미지 중 대표 사용 가능한 첫 이미지
2. 카테고리 기본 썸네일/아이콘
```

## 7.3 등록 필드 → 상세페이지 매핑

| 등록 정보 | 프로젝트 상세 표시 위치 |
|---|---|
| 제목 | 상단 제목 |
| 카테고리 / 세부분야 | 제목 위 Badge / Breadcrumb |
| 한 줄 요약 | 제목 아래 |
| 예산 | `한눈에 보는 프로젝트` + Sticky CTA |
| 작업 기간 | `한눈에 보는 프로젝트` + 일정 |
| 모집 마감 | 상단/요약 + Sticky CTA |
| 진행 방식 | `한눈에 보는 프로젝트` |
| 프로젝트 내용 | 본문 `프로젝트 내용` |
| 원하는 결과물 | 본문 `원하는 결과물` |
| 작업 요청사항 | 본문 `작업 요청사항` |
| 기술 | `필요한 기술 및 도구` |
| 첨부파일 | `참고자료` |
| 의뢰자 | `의뢰자 정보` |

## 7.4 기능

- 단계형 작성
- 임시저장
- 이전 / 다음
- 미리보기
- 등록
- 수정
- 모집 마감
- 작성 중 자동저장 또는 주기적 Draft 저장
- 파일 업로드 진행률
- 파일 형식/용량 검증
- 링크 유효성 기본 검증
- 등록 완료 후 상세 페이지로 이동

## 7.5 수정 제약

프로젝트 상태에 따라 수정 가능 범위를 달리한다.

- `DRAFT`: 전체 수정 가능
- `OPEN`: 제목/설명/조건 수정 가능하되, 이미 지원자가 있는 경우 중요한 조건 변경 시 변경 사실 표시
- `MATCHED` 이후: 공개 공고의 핵심 거래 조건 직접 변경 제한
- `COMPLETED/CLOSED/CANCELLED`: 공고 내용 읽기 전용. CLOSED의 기존 지원자 검토·선정은 허용하는 v2 제안이며 신규 지원은 금지.

예산, 작업 범위, 일정처럼 지원 판단에 직접 영향을 주는 항목이 변경된 경우 기존 지원자에게 알림을 보낼 수 있어야 한다.

# 8. 프로젝트 탐색

프로젝트 탐색의 목표는 수행자가 **짧은 시간 안에 `할 수 있는 일인지 / 보상이 맞는지 / 일정이 가능한지` 판단**하게 하는 것이다.

전문가 탐색과 화면 골격을 공유한다.

```text
공통 Header
→ 페이지 제목/설명
→ 가로 필터바
→ 선택 필터 Chip
→ 결과 수 + 정렬
→ 결과 목록
→ 우측 보조 영역(데스크톱 선택)
```

## 8.1 검색 / 필터

기본:

- 키워드
- 카테고리
- 세부분야(카테고리 패널에 통합, 독립 버튼 없음)
- 예산
- 기간
- 지역/진행 방식
- 마감 임박
- 필요 기술
- 학교 인증
- 기타 조건
- 정렬
- 찜

권장 필터바:

```text
[카테고리 선택] [예산] [기간] [진행 방식] [필요 기술]
[마감 임박 토글] [학교 인증 토글] [초기화]
```

### 데스크톱 Hover/Click 필터

카테고리와 복수 선택 필터는 상단 버튼에 마우스를 올리거나 클릭하면 버튼 바로 아래에 하위 패널을 표시한다.

규칙:

- 한 번에 하나의 필터 패널만 열기
- 버튼 ↔ 패널 사이 포인터 이동 시 닫히지 않도록 hover 영역 연결
- 너무 민감하게 열리지 않도록 짧은 hover 지연 허용
- 패널 바깥 클릭 / `Esc` / 다른 필터 선택 시 닫기
- 복수 선택 필터는 `적용` 버튼 사용 가능
- 즉시 반영형 필터는 선택 후 결과 갱신
- 선택값은 결과 상단 Chip으로 노출
- `필터 초기화`는 전체 선택 상태 복구

```text
그래픽 디자인
- 상세페이지
- SNS·광고 디자인
- 썸네일·카드뉴스
- PPT·인포그래픽
- 웹·앱 UI/UX
- 일러스트·캐릭터
- 편집 디자인

공간·제품 디자인
...

기타 디자인
...
```

### 모바일

- 필터 버튼 클릭 → Bottom Sheet
- 선택 카테고리는 Accordion 또는 Drill-down
- 하단 고정 `결과 보기 N건`
- `초기화` / `적용` 분리

## 8.2 결과 영역

상단:

```text
프로젝트 42건
[서울 전체 ×] [디자인 ×] [예산 10~50만원 ×] [+ 필터 추가]   [최신순 ▾]
```

데스크톱에서는 결과 목록 오른쪽에 선택적으로 다음을 배치할 수 있다.

- 인기 검색어
- 최근 본 프로젝트
- 검색 도움 카드

보조 영역은 핵심 콘텐츠보다 시각적 우선순위를 낮게 유지한다.

## 8.3 프로젝트 카드

프로젝트 카드는 **상세페이지의 축약판**이다.

정보 우선순위:

1. 카테고리
2. 제목
3. 한 줄~2줄 요약
4. 핵심 태그
5. 예산
6. 기간
7. 모집 마감
8. 학교 인증 의뢰자 여부
9. 등록 시각
10. 찜
11. `지원하기`

권장 데스크톱 구조:

```text
┌──────────┬───────────────────────────────┬─────────────────────────┐
│ 썸네일    │ [디자인]                       │ 100,000원   7일   D-5    │
│ 또는      │ 학교 행사 포스터 디자인        │                         │
│ 기본이미지 │ 설명 최대 2줄                  │ 백석대 인증 의뢰자 · 2시간 │
│           │ #포스터 #그래픽디자인 #일러스트 │              [지원하기] │
└──────────┴───────────────────────────────┴─────────────────────────┘
```

### 카드 규칙

- 카드 전체 클릭 → 프로젝트 상세
- CTA 클릭은 카드 이동과 분리
- 설명 최대 2줄
- 태그 최대 3개, 초과 시 `+N`
- 썸네일은 프로젝트 등록 필수 항목이 아님
- 이미지가 없으면 카테고리 기본 썸네일 사용
- 마감 3일 이하 등 임박 정보만 제한적으로 Warning 색 사용
- 금액과 기간은 서로 다른 화면에서도 동일 포맷
- 의뢰자 프로필 사진은 목록 필수 요소가 아님
- 학교 인증은 작은 Badge
- `지원하기`는 `OPEN` 상태에서만 활성
- 이미 지원한 사용자는 `지원 완료` 상태 표시

## 8.4 정렬

권장:

- 최신순
- 마감 임박순
- 높은 예산순

개인화 추천 정렬은 P2 이후.

## 8.5 상태별 카드

- `OPEN`: 지원하기 활성
- 협의 여부는 제안/대화에 표시하며 프로젝트의 지원 가능 여부는 OPEN 및 서버 마감 시각으로 판단
- `MATCHED`: `모집 완료`
- `CLOSED`: `마감`
- `CANCELLED`: 일반 탐색 노출 제외

## 8.6 빈 결과

```text
조건에 맞는 프로젝트가 없습니다.
필터를 줄이거나 다른 키워드로 찾아보세요.

[필터 초기화]
```

## 8.7 프로젝트 상세

프로젝트 상세는 **포트폴리오/전문가 프로필처럼 꾸미는 화면이 아니라, 수행자가 지원 여부를 판단하는 업무 공고 상세 화면**이다.

### 핵심 목표

수행자가 짧은 시간 안에 다음 질문에 답할 수 있어야 한다.

```text
무슨 일인가?
내가 할 수 있는가?
무엇을 만들어야 하는가?
언제까지 해야 하는가?
보상은 얼마인가?
어떻게 지원하는가?
```

### 정보 구조

#### 상단

- Breadcrumb
- 카테고리 / 세부분야 Badge
- 제목
- 한 줄 요약
- 학교 인증 의뢰자 Badge
- 등록 시각
- 조회수(선택)
- 기술/업무 태그
- 찜
- 공유

#### `한눈에 보는 프로젝트`

- 예산
- 작업 기간
- 모집 마감
- 지원자 수
- 진행 방식
- 선택적으로 희망 시작일

예:

```text
예산          작업 기간        모집 마감        지원자       진행 방식
100,000원     약 7일           D-5             8명          온라인
```

#### 본문

순서:

1. 프로젝트 내용
2. 원하는 결과물
3. 작업 요청사항
4. 필요한 기술 및 도구
5. 일정 안내
6. 참고자료(선택)
7. 의뢰자 정보
8. 비슷한 프로젝트(선택)

### 이미지 정책

- 프로젝트 대표 이미지는 **필수 아님**
- 프로젝트 상세 상단에 대형 Hero/Gallery를 기본 배치하지 않음
- 이미지가 있으면 `참고자료`로 표시
- 디자인/영상 등 참고 이미지가 중요한 카테고리는 첨부 미리보기를 제공할 수 있음
- 이미지가 없어도 화면 완성도가 떨어져 보이지 않게 텍스트/조건 중심 레이아웃 유지

### 우측 Sticky CTA

데스크톱:

```text
모집중                          D-5

예산
100,000원

[지원하기]
[문의하기]
[♡ 프로젝트 저장]

✓ 백석대학교 인증 의뢰자
```

Sticky 영역에는 본문에서 이미 충분히 설명한 내용을 반복하지 않는다.

### 상태에 따른 CTA

- 본인 프로젝트: `지원하기` 대신 `수정하기 / 지원자 보기 / 모집 마감`
- 이미 지원함: `지원 완료 / 내 지원 보기`
- `MATCHED`: `모집 완료`
- `CLOSED`: `마감된 프로젝트`
- `CANCELLED`: 지원 불가
- 미인증 사용자: 학교 인증 안내 후 지원 가능

### 의뢰자 정보

최소 신뢰 정보만 표시한다.

- 이름 또는 플랫폼 표시명
- 학교 인증
- 공개 허용 시 학부/학과
- 완료 의뢰 수
- 받은 후기 요약

이메일 / 전화번호 / 학번 / 직번은 공개하지 않는다.

### 프로젝트 상세과 등록 화면의 관계

프로젝트 상세은 의뢰자가 직접 꾸미는 문서가 아니다.

```text
등록 폼 입력
→ 시스템이 표준 레이아웃으로 정리
→ 프로젝트 상세 자동 생성
```

따라서 상세페이지의 시각적 완성도는 등록자의 디자인 능력에 의존하지 않아야 한다.

# 9. 전문가 탐색

전문가 탐색은 프로젝트 탐색과 동일한 페이지 골격을 사용하되, 판단 기준을 `예산/마감`이 아니라 **대표 작업물 / 전문 분야 / 신뢰 정보**로 바꾼다.

## 9.1 검색 / 필터

- 이름 / 키워드
- 전문 분야
- 세부분야(전문 분야 패널에 통합)
- 기술
- 지역
- 후기
- 완료 프로젝트
- 현재 의뢰 가능
- 학교 인증
- 기타 조건
- 정렬
- 찜

권장 필터바:

```text
[전문 분야 선택] [기술] [후기] [완료 프로젝트]
[현재 의뢰 가능 토글] [학교 인증 토글] [초기화]
```

프로젝트 탐색과 동일한 Hover/Click Mega Menu 패턴을 재사용한다.

카테고리 명칭은 화면 목적에 맞게 `카테고리 선택` 대신 `전문 분야 선택`으로 표시한다.

## 9.2 결과 상단

```text
전문가 42명
[디자인 전체 ×] [후기 4.5 이상 ×]   [리뷰 많은순 ▾]
```

정렬:

- 리뷰 많은순
- 평점 높은순
- 완료 프로젝트 많은순
- 최신 활동순

신규 전문가를 과도하게 불리하게 만드는 단일 랭킹은 피한다.

## 9.3 전문가 카드

전문가 카드는 **이력서 카드가 아니라 미니 포트폴리오 카드**다.

프로필 사진은 필수가 아니며, 목록에서는 **대표 포트폴리오 이미지가 주 시각 요소**다.

표시 우선순위:

1. 대표 포트폴리오 이미지
2. 이름 / 활동명
3. 전문 분야
4. 한 줄 소개
5. 핵심 태그 최대 3개
6. 평점 / 후기 수
7. 완료 작업 수
8. 응답 정보
9. 학교 인증
10. 프로필 CTA
11. 찜

권장 구조:

```text
┌────────────┬───────────────────────────────────────────────┐
│ 대표 작업물 │ [디자인]                                      ♡ │
│ 이미지      │ 김서연 | 브랜드·그래픽 디자이너                 │
│            │ 브랜드의 가치를 시각적으로 표현하는 디자이너입니다.│
│            │ #브랜딩 #포스터 #로고디자인                      │
│            │ ★ 4.9 (32) · 작업 28건 · 평균 2시간 내 응답       │
│            │ ✓ 백석대 인증                        [프로필 보기] │
└────────────┴───────────────────────────────────────────────┘
```

### 카드 규칙

- 프로필 사진을 별도 표시하지 않아도 됨
- 대표 이미지가 전문가의 실력 판단에 가장 큰 면적을 차지
- 이름은 강하게, 학교 인증은 보조 Badge
- 소개는 최대 1~2줄
- 태그는 최대 3개
- 평점이 없으면 `신규` 또는 미표시
- 완료 건수는 신규 사용자를 평가절하하지 않도록 보조 정보로 사용
- 현재 의뢰 가능 상태는 필요 시 작은 Success Badge로 표시
- `프로필 보기`가 Primary CTA
- 카드 전체 클릭도 공개 프로필로 이동 가능

## 9.4 우측 보조 영역

데스크톱에서 선택적으로:

- 인기 전문가 분야
- 최근 본 전문가
- 전문가 찾기 도움말

프로젝트 탐색과 동일한 폭/스타일을 사용하여 두 화면의 학습 비용을 낮춘다.

## 9.5 빈 결과

```text
조건에 맞는 전문가가 없습니다.
기술이나 전문 분야 조건을 줄여보세요.

[필터 초기화]
```

## 기능


# 22. 주요 상태값

> 아래 v2 상태는 백엔드 제안안이다. 현재 데모가 전체 전이를 구현한 것은 아니다. 주체·가드·원자성은 [데이터·API 계약](데이터_API_계약.md)의 4장을 기준으로 검토한다.

## 프로젝트

```text
DRAFT
OPEN
MATCHED
IN_PROGRESS
COMPLETION_REQUESTED
COMPLETED
CLOSED
CANCELLED
```

협의는 제안/대화 상태, 계약 체결은 계약 SIGNED로 관리한다. 분쟁은 별도 disputeStatus로 관리해 기존 업무 상태를 잃지 않게 한다. CLOSED는 모집 종료이며 기존 지원자 선정 가능.

## 제안 / 견적

```text
SUBMITTED
WITHDRAWN
REJECTED
IN_DISCUSSION
SELECTED
```

## 지정 요청

```text
PENDING
ACCEPTED
REJECTED
EXPIRED
CANCELLED
```

## 계약

```text
DRAFT
WAITING_ACCEPTANCE
SIGNED
SUPERSEDED
CANCELLED
```

열람 여부와 분쟁은 별도 기록. SIGNED 버전은 불변이며 SUPERSEDED는 대체된 미체결 버전에 적용한다.

## 포트폴리오

```text
DRAFT
PUBLIC
PRIVATE
HIDDEN_BY_ADMIN
```

## 완료 작업 포트폴리오 공개

```text
NOT_REQUESTED
PENDING_APPROVAL
APPROVED
REJECTED
```

## 문의 / 신고

# 24. 화면 공통 요구사항

- PC / 모바일 반응형
- 카드 기반 탐색
- **전문가/포트폴리오는 이미지·작업물 우선, 프로젝트 상세는 텍스트·조건 우선**
- 프로젝트 등록은 단계형
- 포트폴리오 등록은 최소 필드 우선
- 주요 상태는 Badge
- 목록 검색 / 필터 / 정렬
- 데스크톱 주요 필터는 Hover/Click Dropdown 또는 Mega Menu
- 모바일 필터는 Bottom Sheet
- 적용된 필터는 결과 상단 Chip으로 표시
- 필터 전체 초기화와 개별 Chip 제거 모두 지원
- 상세 화면 주요 CTA는 Sticky
- 로딩 / 빈 결과 / 오류 / 권한 없음 / 마감 별도 상태
- 이메일, 전화번호, 학번/직번 목록 직접 노출 금지
- 파일 형식 / 용량 표시
- 모든 중요 작성 폼 임시저장 또는 이탈 경고
- 사용자가 같은 정보를 여러 화면에서 반복 입력하지 않도록 함
- 카드 전체 클릭과 내부 CTA 클릭 이벤트가 충돌하지 않게 처리
- 텍스트 길이 초과 시 카드에서는 말줄임, 상세에서는 전체 표시
- Keyboard Focus / `Esc` 닫기 등 기본 접근성 지원
- Hover 전용 기능은 반드시 Click으로도 접근 가능해야 함
- 필터/정렬/검색 상태는 가능하면 URL Query에 반영하여 뒤로가기/공유 시 유지

# 26. 이 플랫폼의 핵심 차별 기능

개발 중 기능 범위가 흔들릴 경우 아래 5개를 우선한다.

```text
1. 작업물 중심 공개 프로필
2. 별도의 작업물 탐색
3. 지원 시 기존 대표작 재사용
4. 매칭 후 프로젝트 워크룸
5. 실제 완료 프로젝트 → 검증 포트폴리오 경력
```

이 구조를 유지해야 긱창업이 단순한 교내 인력 모집 게시판이 아니라  
**학생의 실력 발견 → 실제 의뢰 → 경험 축적 → 다음 의뢰로 연결되는 선순환 플랫폼**이 된다.
