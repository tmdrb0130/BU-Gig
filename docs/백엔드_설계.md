# 백엔드 구현 설계

기준일: 2026-09-30 · 상태: **구현 전 설계 제안**

현재 `backend/`에는 `.gitkeep`만 있다. 프론트엔드는 브라우저 저장소 기반 데모이며 이 문서의 서버, DB, API는 아직 구현되지 않았다. 언어·프레임워크·배포 사업자는 미정이다.

이 문서는 백엔드 내부 구조와 구현 단위를 설명한다. 전체 구성은 [시스템 아키텍처](시스템_아키텍처.md), 엔터티·상태·경로의 기준은 [데이터·API 계약](데이터_API_계약.md), 단계별 인수 조건과 미결정 사항은 [개발·검증 계획](개발_검증_계획.md)을 따른다.

## 1. 구현 범위

한 계정이 의뢰자와 수행자로 모두 활동한다. 프로젝트를 등록하고 지원자를 선정하는 흐름과 전문가에게 지정 요청을 보내는 흐름을 같은 매칭·워크룸 모델로 연결한다.

| 영역 | 서버가 담당할 일 | 완료 판단 |
| --- | --- | --- |
| 계정·인증 | 가입, 로그인, 세션, 이메일 확인, 비밀번호 재설정 | 다른 브라우저에서도 같은 계정으로 접근하고 로그아웃 세션을 재사용할 수 없음 |
| 학교 인증·프로필 | 인증 이력, 소개·분야·기술·경력, 공개 정보 | 학교 인증과 공개 프로필을 독립적으로 관리 |
| 탐색 | 프로젝트·전문가·작업물 검색, 필터, 페이지 | 목록·건수·상세의 공개 범위와 검색 조건이 일치 |
| 의뢰·매칭 | 초안, 게시, 지원, 선정, 지정 요청·견적 | 프로젝트당 선정과 워크룸이 각각 한 번만 생성 |
| 협업 | 참여자, 메시지, 읽음, 첨부, 계약 버전·동의 | 당사자만 접근하고 같은 계약 버전에 양측 동의 |
| 완료·신뢰 | 완료 요청·보완·승인, 후기, 작업물 공개 승인 | 완료된 거래의 당사자·승인된 버전만 인정 |
| 운영 | 알림, 문의·신고, 인증 심사, 감사로그, 복구 | 처리 권한과 변경 사유를 추적하고 실패 작업을 재처리 |

결제·정산·에스크로·외부 전자서명은 1차 범위 밖이다. 포트폴리오 등록·수정 화면과 콘텐츠 블록 스키마는 기존 디자인 대기 상태를 유지한다.

## 2. 내부 계층과 코드 배치

하나의 백엔드 앱 안에서 도메인별 모듈을 나눈다. 다음은 논리 구조이며 프레임워크 선정 후 실제 패키지·디렉터리 규칙에 맞춘다.

```text
backend/
  src/
    bootstrap/                 앱 시작, 설정 조립, API/Worker 실행
    modules/
      identity/                계정·세션·메일 토큰·약관 동의
      verification/            학교 인증 신청·심사·만료
      profile/                 공개 프로필·경력·제공 서비스
      taxonomy/                분야·기술·별칭 사전
      portfolio/               작업물·버전·대표작·공개 승인
      project/                 의뢰 초안·게시·모집 종료
      matching/                지원·지정 요청·견적·선정
      collaboration/           워크룸·대화·메시지·읽음
      contract/                계약 버전·발행·동의
      delivery/                완료 요청·보완·승인·후기
      media/                   업로드·검사·연결·다운로드
      notification/            수신자별 알림·발송
      operations/              문의·신고·감사
    shared/                    ID·시간·공통 오류 등 최소 공용 코드
    infrastructure/            DB·객체 저장소·메일·이벤트 어댑터
  migrations/                  순서가 있는 DB 변경 이력
  contracts/                   OpenAPI 및 요청·응답 예제
  tests/                       도메인·DB 통합·API 계약 테스트
```

| 계층 | 책임 | 예시 |
| --- | --- | --- |
| HTTP 경계 | 요청 형식 검사, 인증 주체 전달, 응답 변환 | 선정 요청의 proposalId·expectedVersion 검사 |
| 애플리케이션 서비스 | 권한 확인, 유스케이스 실행, 트랜잭션 경계 | SelectProposal, AcceptDirectRequest |
| 도메인 | 상태 전이·불변 조건 | 이미 선정된 의뢰에 추가 선정 금지 |
| 저장소·외부 어댑터 | DB 접근, 메일·파일·실시간 전달 | ProjectRepository, MailAdapter |

컨트롤러가 다른 모듈의 테이블을 직접 갱신하지 않는다. 모듈 간 변경은 명시적인 서비스 호출로 묶고, 즉시 일관성이 필요한 선정·계약·완료는 같은 DB 트랜잭션을 사용한다. 메일·PDF·파일 검사는 커밋 후 작업자로 넘긴다.

## 3. 요청 처리와 공통 규칙

1. requestId를 부여하고 요청 크기·형식·허용 필드를 검사한다.
2. 비공개 API는 서버 세션으로 행위자를 확인한다. 상태 변경에는 CSRF·Origin 검증을 적용한다.
3. 대상 조회 후 소유자·참여자·학교 인증·현재 상태를 확인한다.
4. 변경 요청의 버전과 멱등 키를 확인하고 트랜잭션을 실행한다.
5. DB 변경과 필요한 Outbox 이벤트를 함께 저장한다.
6. 커밋 성공 후 공개 범위를 제한한 DTO를 반환한다.

사용자 ID·소유자·배지·완료 건수·체결 상태는 클라이언트 입력을 신뢰하지 않는다. 공개 프로필과 내 계정 응답은 서로 다른 DTO로 정의한다. 성공·오류 envelope와 상태 코드는 데이터·API 계약을 그대로 사용하며, `204` 응답에는 본문을 넣지 않는다.

버전 충돌은 `409`로 반환하고 클라이언트가 새 상태를 조회하도록 한다. 트랜잭션 재시도는 일시적인 DB 충돌에 한정한다. 권한 부족·마감·잘못된 상태 등 도메인 실패는 자동 재시도하지 않는다.

## 4. 핵심 트랜잭션

| 명령 | 같은 트랜잭션으로 처리할 변경 | 중복·경쟁 방지 |
| --- | --- | --- |
| 공개 의뢰 지원 | 유효 의뢰 확인, 지원서·대표작 스냅샷, 알림 이벤트 | 의뢰+지원자 unique, 모집 마감 시각 재검사 |
| 지원자 선정 | 의뢰 잠금, 지원 검증, Match·Workroom, 대화 연결, 다른 지원 결과, 이벤트 | 프로젝트별 Match·Workroom unique, expectedVersion |
| 지정 요청 수락 | 최신 조건 확인, DIRECT_ONLY 의뢰·Match·Workroom, 요청 상태, 이벤트 | 요청별 매칭 unique, 최신 견적 버전, 만료 검사 |
| 계약 동의 | 현재 검토 버전·해시 검사, 당사자 동의, 양측 체결 여부, 프로젝트 상태, 이벤트 | 버전+동의자 unique, 계약 단위 잠금/버전 검사 |
| 완료 승인 | 활성 완료 요청 승인, 프로젝트 COMPLETED, 집계 반영용 이벤트 | 동일 요청 중복 승인 차단, 프로젝트 상태·버전 검사 |
| 메시지 전송 | 참여 권한, 메시지·방 내부 순번, 이벤트 | 방+발신자+clientMessageId unique |

선정 시 기존 문의 대화가 있으면 해당 지원자의 대화만 연결한다. 없다면 두 당사자의 대화를 생성한다. 미선정자의 대화나 첨부를 선정된 워크룸에 노출하지 않는다.

명령 재전송은 같은 결과를 돌려주도록 설계한다. 멱등 기록은 사용자·메서드·정규 경로·키·요청 본문 해시에 연결하고, 동시 요청 중 하나만 실행되게 한다. 커밋 후 응답이 유실되어도 다시 선정하거나 계약 동의를 중복 생성하지 않아야 한다.

## 5. DB 변경과 비동기 처리

DB 초기안은 기존 아키텍처의 PostgreSQL 제안을 따른다. 실제 컬럼·FK·unique·인덱스·삭제 정책은 데이터·API 계약을 기준으로 migration에 작성한다. 서버 시작 때 운영 테이블을 자동 초기화하지 않는다.

- 기준 데이터: 분야·기술·약관 버전은 명시적 seed로 관리한다. 데모 사용자·후기·인증 배지는 운영 seed에 포함하지 않는다.
- 시간: UTC 저장·전송, Asia/Seoul 화면 표시. date-only와 마감 시각을 구분한다.
- 동시성: 선정·수락·동의·완료의 unique 제약은 애플리케이션 사전 검사와 함께 적용한다.
- 변경 배포: 새 컬럼 추가 → 호환 앱 배포 → 데이터 이관 → 제약 강화 → 이전 컬럼 제거 순으로 나눈다.
- 복구: 앱 롤백과 데이터 복구를 구분하고, 파괴적 migration 전에 복구 절차를 검증한다.

Outbox는 업무 데이터와 함께 커밋한다. Worker는 처리 대상을 일정 시간 점유하고 성공·실패·다음 실행 시각을 기록한다. 재시도 상한에 도달한 작업은 별도 실패 상태로 두고 운영자가 사유를 확인해 재처리한다. 이벤트 소비자는 eventId로 중복 효과를 방지한다.

메일 공급자의 멱등 기능이 없다면 발송 직후 장애로 인한 중복 메일 가능성까지 완전히 제거할 수는 없다. 발송 기록과 공급자 메시지 ID를 추적하며, 메일 중복이 선정·체결 등 업무 변경을 다시 실행하게 만들지 않는다.

## 6. 프론트엔드 연결 지점

| 현재 파일 | 현재 역할 | 서버 연동 시 변경 |
| --- | --- | --- |
| `frontend/src/auth.js`, `Auth.jsx` | 브라우저 계정·세션, 인증 화면 | `/auth/*` 호출과 인증 초기화, 서버 오류 표시 |
| `frontend/src/store.jsx` | 프로젝트·찜·지원·요청을 localStorage에 저장 | 기능별 조회·변경 API로 전환, 계정 전환 시 캐시 정리 |
| `frontend/src/forms.jsx` | 로컬 의뢰 등록·지원·지정 요청 | 초안 저장·게시·지원 API와 업로드 상태 연결 |
| `frontend/src/pages.jsx` | 데모 탐색·상세·MY | 서버 목록·건수·상세·계정별 MY, 로딩·빈 결과·오류 |
| `frontend/src/lib.js`, `FieldFilter.jsx` | 로컬 필터·정렬·URL 조건 | 공유 URL을 서버 쿼리로 변환, 검색 규칙 일치 |
| `frontend/src/Workroom.jsx` | 단일 예시 방·로컬 메시지·파일·내 동의 | 방 ID별 조회, 메시지 API·SSE, 계약 버전·실제 파일 |
| `frontend/src/data.js` | 예시 인물·의뢰·작업물·이미지 매핑 | 데모 fixture 분리, 운영 데이터는 서버에서 조회 |

프론트 경로 `/works`는 유지하면서 API `/portfolios`로 매핑할 수 있다. 운영 워크룸의 프론트 경로는 `/workrooms/:id`를 제안한다. 기존 `/workroom`은 API 전환 시 내 방 목록 안내 또는 명시적 데모 경로로 정리한다.

새로 둘 `frontend/src/api/`에서 `/api/v1` 접두어, 세션 쿠키, CSRF, requestId, 오류 변환을 공통 처리한다. HTTP 타임아웃 후 변경 요청을 무조건 재전송하지 않고 멱등 키와 서버 조회로 결과를 확인한다. API 장애를 데모 데이터로 대체하지 않는다.

브라우저 계정·해시·계약 동의는 운영 데이터로 자동 이관하지 않는다. 의뢰 초안은 로그인한 사용자가 내용을 확인한 뒤 새 서버 초안으로 저장하는 방식만 제안한다.

## 7. 환경 구성과 실행 준비물

아래는 설정 계약 제안이다. 실제 환경 변수나 실행 명령이 구현된 상태는 아니다.

| 설정 그룹 | 필요한 값 | 주입 위치 |
| --- | --- | --- |
| 앱 | 실행 환경, 포트, 서비스 공개 URL | API·Worker |
| DB | 연결 주소, 계정, 연결 풀 설정 | API·Worker·migration 작업 |
| 세션 | 쿠키 이름, 세션 수명, 허용 Origin | API |
| 파일 | 저장소 endpoint·bucket·자격 증명, 업로드 제한 | API·검사 Worker |
| 메일 | 발송 어댑터 자격 증명, 발신 주소, 개발용 수신함 | 메일 Worker |
| 작업 | 재시도 횟수, backoff, lease 시간 | Worker |
| 관측 | 로그 수준, 오류 수집 주소, 모니터링 설정 | API·Worker |

브라우저에는 공개 가능한 API 경로만 전달한다. DB 비밀번호·메일 키·객체 저장소 비밀은 프론트 빌드 환경 변수에 넣지 않는다. 추후 `.env.example`에는 이름과 예시만 기록하고 실제 값은 환경별 비밀 관리로 주입한다.

로컬 구성은 프론트 dev 서버 + API + 개발 DB + 개발 메일함 + 개발 객체 저장소를 제안한다. 운영은 같은 origin에서 SPA와 `/api/v1/*`를 분기하며, SSE도 `/api/v1/events`로 전달한다. liveness는 프로세스 생존, readiness는 필수 의존성 사용 가능 여부를 구분하고 상세 오류·비밀은 공개하지 않는다.

## 8. 첫 구현 묶음과 검증

1. 스택과 실행 환경 확정 후 앱 시작·설정 검증·DB migration·공통 오류·OpenAPI를 준비한다.
2. 가입·로그인·세션 조회·로그아웃과 두 사용자 데이터 분리를 구현한다.
3. 분야 사전·학교 인증·프로필을 연결한다. 실제 인증 수단이 정해지기 전 테스트 인증 fixture는 개발 환경에만 둔다.
4. 의뢰 초안·게시·공개 목록·상세를 연결해 다른 기기에서도 같은 결과를 확인한다.
5. 지원 → 선정 → 워크룸 생성까지 한 흐름을 완성한 뒤 지정 요청·계약·완료를 확장한다.
