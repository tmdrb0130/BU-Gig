# 05. 핵심 시퀀스

기준일: 2026-10-01 · 상태: **구현 전 처리 순서 제안**

모든 경로는 `/api/v1` 아래다. 아래 DB 작업 묶음은 한 트랜잭션이며 실패하면 전체 롤백한다. 세션·CSRF·권한은 [07](07_권한_매트릭스.md), 전이는 [04](04_도메인_상태도.md), 비동기 처리는 [08](08_파일_이벤트_흐름.md)을 따른다.

## 1. 지원 제출

```mermaid
sequenceDiagram
    actor Applicant as 지원자
    participant UI as 프론트
    participant API as API
    participant DB as DB
    participant Worker as Worker
    Applicant->>UI: 제안·금액·기간·대표작 선택
    UI->>API: POST /projects/:id/proposals + 멱등 키
    API->>API: 세션·CSRF·학교 인증·입력 검사
    API->>DB: BEGIN / 멱등 키 확보 / Project 잠금
    API->>DB: OPEN·마감·본인 여부·중복 검사
    API->>DB: 대표작 소유·버전·공유 동의·READY 검사
    API->>DB: Proposal·Revision·자료 snapshot·Outbox·응답 기록
    API->>DB: COMMIT
    API-->>UI: 201 proposalId·revisionId·status
    UI-->>Applicant: 지원 완료 및 내 지원 갱신
    Worker->>DB: Outbox → 의뢰자 알림·사용자 이벤트
```

대표작은 선택 시 조회한 버전을 제출한다. 비공개 작업은 해당 의뢰자에게 공유한다는 명시적 동의를 요구한다. 서버가 제출 revision을 확정하기 전 성공 UI를 표시하지 않는다. 잘못된 필드 422, 중복 409, 인증 부족 403, 비공개 대상 404다.

## 2. 지원자 선정

```mermaid
sequenceDiagram
    actor Owner as 의뢰자
    participant API as Workflow
    participant DB as DB
    participant Worker as Worker
    Owner->>API: POST /projects/:id/selection
    Note over Owner,API: proposalId, proposalRevisionId, expectedVersion, 멱등 키
    API->>DB: BEGIN / 멱등 키 확보 / Project → Proposal 잠금
    API->>DB: 소유자·현재 공고 revision 확인·유효 지원 검사
    alt 이미 다른 선정 또는 revision 변경
        API->>DB: ROLLBACK
        API-->>Owner: 409 및 재조회 안내
    else 선정 가능
        API->>DB: Match와 조건 snapshot 생성
        API->>DB: 선택 지원 SELECTED / 다른 활성 지원 REJECTED
        API->>DB: 해당 지원자의 대화 연결 또는 신규 생성
        API->>DB: Workroom·Contract·첫 DRAFT 생성
        API->>DB: Project MATCHED·Outbox·멱등 응답 저장
        API->>DB: COMMIT
        API-->>Owner: matchId·workroomId·contractId
        Worker->>DB: 양측 및 미선정자별 알림, 방 시스템 메시지
    end
```

다른 지원자의 문의 대화·첨부를 선정 방에 합치지 않는다. 첫 초안은 선택한 revision과 공고 조건을 근거로 생성하며 의뢰자가 발행 전에 확인한다. 금액·일정 차이는 조용히 덮지 않는다. SELECTED와 MATCHED가 생겨도 계약은 아직 DRAFT다.

## 3. 지정 요청 수락

```mermaid
sequenceDiagram
    actor Sender as 원래 발신자
    actor Recipient as 원래 수신자
    participant API as API
    participant DB as DB
    Sender->>API: POST /direct-requests / ORIGINAL 조건
    API->>DB: PENDING 요청·terms v1·Outbox
    API-->>Sender: requestId·latestTermsId·version
    opt 조건 변경 회신
        Recipient->>API: POST /direct-requests/:id/quotes + expectedVersion
        API->>DB: 요청 잠금 / QUOTE 새 버전 / latestTermsId 갱신
        API-->>Recipient: 새 termsId·version
    end
    Note over Sender,Recipient: ORIGINAL은 수신자, QUOTE는 원래 발신자만 수락
    Sender->>API: QUOTE 수락 예: termsId·expectedVersion·멱등 키
    API->>DB: BEGIN / 요청 잠금 / 역할·만료·최신 terms 확인
    API->>DB: DIRECT_ONLY MATCHED Project·revision·Match 생성
    API->>DB: 대화·Workroom·Contract DRAFT 생성
    API->>DB: ACCEPTED·acceptedTermsId·Outbox·응답 기록
    API->>DB: COMMIT
    API-->>Sender: projectId·workroomId
```

견적 없는 ORIGINAL 수락도 마지막 수락 단계의 행위자만 수신자로 바뀐다. 수락과 만료·견적 갱신·취소가 경쟁하면 같은 요청 잠금으로 순서를 정한다. 이미 수락된 동일 멱등 요청에는 기존 방을 반환한다.

## 4. 계약 발행·동의

```mermaid
sequenceDiagram
    actor A as 버전 작성 당사자
    actor B as 상대 당사자
    participant API as API
    participant DB as DB
    participant Worker as PDF Worker
    A->>API: POST /contract-versions/:id/publish
    API->>DB: Project → Contract 잠금 / 허용 상태 검사
    API->>DB: 전체 조건·body hash 확정 / WAITING_ACCEPTANCE·Outbox 커밋
    API-->>A: versionId·contentHash·contractVersion
    A->>API: POST /contract-versions/:id/acceptances
    API->>DB: 같은 검토본·해시 검사 / A 동의 커밋
    B->>API: GET /contracts/:id
    API-->>B: 현재 검토본·A 동의·최신 Contract version
    B->>API: POST /contract-versions/:id/acceptances
    API->>DB: Project → Contract 잠금 / 버전·해시 재확인
    API->>DB: B 동의 / 양측 확인 / SIGNED·signed 포인터 갱신
    API->>DB: 최초 체결만 IN_PROGRESS / PDF Job용 Outbox 커밋
    API-->>B: SIGNED·documentStatus=PENDING
    Worker->>DB: 해당 불변 체결본 조회
    Worker->>Worker: PDF 생성·비공개 저장
    Worker->>DB: 문서 READY 또는 실패 재시도 기록
```

각 동의는 별도 멱등 키를 사용한다. 두 동의가 동시에 들어와 expectedVersion이 충돌하면 한쪽은 재조회 후 동일 내용인지 확인해 재시도한다. 검토본이 바뀌었다면 자동 동의하지 않는다. 변경 계약 체결 후에도 이전 체결본은 이력으로 남는다.

## 5. 완료 요청·승인

```mermaid
sequenceDiagram
    actor Provider as 수행자
    actor Owner as 의뢰자
    participant API as API
    participant DB as DB
    participant Worker as Worker
    Provider->>API: POST /workrooms/:id/completion-requests
    Note over Provider,API: signedVersionId, note, READY mediaIds, expectedVersion
    API->>DB: Project → Contract 잠금 / 검토본·취소·분쟁 없음 검사
    API->>DB: 기준 체결본 고정 / PENDING·COMPLETION_REQUESTED·Outbox 커밋
    Owner->>API: GET /completion-requests/:id
    API-->>Owner: 기준 계약·산출물·요청 version
    alt 보완 필요
        Owner->>API: POST /completion-requests/:id/request-changes + 사유
        API->>DB: CHANGES_REQUESTED·Project IN_PROGRESS·Outbox 커밋
    else 완료 승인
        Owner->>API: POST /completion-requests/:id/approve + 멱등 키
        API->>DB: Project → Contract → 요청 잠금 / 현재 체결본·상태 재확인
        API->>DB: APPROVED·COMPLETED·Outbox·멱등 응답 커밋
        API-->>Owner: COMPLETED·후기 작성 가능
        Worker->>DB: 완료 역할별 집계·알림 멱등 반영
    end
```

완료 허용 여부는 집계 반영을 기다리지 않고 Project 원천 상태로 판단한다. 보완 후 재요청은 새 completionRequest를 만들며 이전 기록을 수정하지 않는다. 완료 후 후기·작업물 공개 승인은 별도 명령이다.

## 6. 공통 실패 복구

| 실패 | 처리 |
| --- | --- |
| 커밋 전 오류 | 롤백, 성공 알림 없음, 폼 입력 유지 |
| 커밋 후 HTTP 응답 유실 | 같은 키·같은 body로 재요청해 저장된 결과 수신 |
| 같은 키 다른 body | 409 IDEMPOTENCY_KEY_REUSED, 새 행동은 새 키 |
| 멱등 보관 만료 | 도메인 unique와 현재 상태 검사로 중복 효과 방지; 기존 성공 응답 재현은 보장하지 않음 |
| Worker 지연·메일 실패 | 업무 상태 유지, Job 재시도·운영 경보 |
| SSE 유실 | 상세 REST와 cursor 재조회로 복구 |
| 계정·권한 변경 | 응답 재생 때도 접근 재검사, 세션·SSE 종료, 개인 캐시 제거 |
