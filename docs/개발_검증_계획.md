# 개발 순서·인수 기준·미결정 사항

기준일: 2026-09-30 · 목적: 문서상의 기능을 실제 다중 사용자 서비스로 전환하기 위한 실행 기준

## 1. 이번 문서 정비의 범위

- 현재 구현과 목표 명세를 분리하고 오래된 헤더·필터 규칙을 수정한다.
- 기존 프론트엔드를 버리지 않고 API로 단계적으로 전환하는 기준을 정한다.
- 포트폴리오 등록/수정 화면은 디자인 대기다. 사용자의 시안을 받기 전 새 편집기를 구현하지 않는다.
- 신규 백엔드·데이터베이스·배포·외부 발송은 이번 문서 작업에 포함되지 않는다.

## 2. 개발 단계와 완료 조건

백엔드 모듈·계층·환경 준비물과 프론트 파일별 연결 지점은 [백엔드 구현 설계](백엔드_설계.md)를 참조한다. 아래 단계의 API 경로·상태·데이터 제약은 [데이터·API 계약](데이터_API_계약.md)을 기준으로 구체화한다.

| 단계 | 작업 | 완료 조건 / 선행 의존 |
| --- | --- | --- |
| 0. 설계 승인 | 아래 결정 항목, 상태 전이, 공개 범위, API schema 확정 | 스택·인증 수단·운영자·환경 책임 확정. OpenAPI 리뷰 |
| 1. 서버 기반 | 모듈 구조, DB migration, 세션, 가입/로그인/재설정, 오류·로그·CI | 두 사용자 세션 분리, 쿠키/CSRF/속도 제한, 스테이징 smoke test |
| 2. 계정·분야·프로필 | 학교 인증, taxonomy, 내 프로필/경력, 공개 DTO, 관리자 인증 심사 | 인증 위조 불가, 비공개 정보 미노출, 배지 만료 반영 |
| 3. 탐색·의뢰 | 목록/상세 API, URL 어댑터, 프로젝트 draft/publish/edit/close, 파일 파이프라인 | 필터 의미 동일, 권한·마감·업로드 검증, 실제 저장된 의뢰 재조회 |
| 4. 지원·지정 요청 | 지원/대표작 연결, 받은 지원, 선정, 요청 수락/견적/거절 | 동시 선정 1건, 중복 클릭 멱등, 두 매칭 경로가 같은 워크룸 생성 |
| 5. 협업·계약 | 대화 목록/채팅/읽음, 워크룸, 버전·양측 동의·PDF | 타인 방 접근 불가, 재연결 복구, 구버전 동의 거절 |
| 6. 완료·신뢰·운영 | 완료 요청/보완/승인, 후기, 알림, 신고·감사·기본 관리 | 실거래 후기만 허용, 담당자 처리·백업 복구·폐기 정책 검증 |
| 별도 디자인 트랙 | 포트폴리오 작성/수정 시안 → schema 합의 → 구현 | 시안 승인 후 시작. 단계 4 대표작 연결과 검증 포트폴리오의 의존 기능 |

포트폴리오 화면 승인 전 서버 테스트에는 합성 포트폴리오 fixture를 사용한다. 운영에서 모든 회원이 예시 포트폴리오를 자신의 작업처럼 제출하게 하지 않는다. 무포트폴리오 지원 허용 여부는 D-07 결정에 따른다.

기존 P0/P1 목록의 우선순위는 제품 기능 중심이었다. **권한·최소 신고 대응·핵심 감사로그·백업은 공개 운영 전 필수**로 올린다. UI가 존재한다는 이유로 서버 검증을 후순위로 미루지 않는다.

## 3. 프론트엔드 전환 체크리스트

- [ ] `frontend/src/data.js` seed와 실 API 모드를 명확히 분리. 운영 빌드에 예시 후기/인증 배지가 실제 데이터로 노출되지 않음.
- [ ] `store.jsx` 전역 로컬 상태를 기능별 서버 상태로 대체. 인증 user와 ownerId 연결.
- [ ] `forms.jsx`의 고정 `ownerId: "me"`, 표시명, localStorage 자동등록 제거.
- [ ] 로컬 계정/해시/세션은 서버로 자동 이관하지 않음. 운영 가입·이메일 확인을 새로 진행.
- [ ] 기존 draft 이관은 로그인 사용자에게 내용을 보여주고 명시적으로 승인받음. 제출/계약/파일의 소유권을 로컬 데이터로 증명하지 않음.
- [ ] 초기 로그인 로딩·401 재로그인·403 학교 인증·404 비공개/삭제·409 변경 충돌·429 재시도 상태 구현.
- [ ] 회원 A 로그아웃 후 B 로그인 시 A의 캐시·초안·방·알림·파일 URL 노출 없음.
- [ ] 필터 프리셋/직접 입력의 예산 구간 규칙 일치, unknown verified는 인증 결과에서 제외.
- [ ] 카테고리명 JSON URL 호환 → 표준 분야 ID API 변환, 잘못된/폐기된 값 안내.
- [ ] 기존 `/workroom`은 데모로 분리하거나 내 방 목록으로 이동, 운영 방은 ID 경로 사용.
- [ ] 저장 중 재클릭 방지, 실패 시 입력 보존, 성공 후 목록/상세 캐시 갱신.
- [ ] 업로드 진행/검사 중/실패/취소/용량 초과를 구분. 실제 서버 저장 전 완료 표시 금지.

## 5. UI·접근성·반응형 인수 기준

- 화면 폭 320/390/768/820/1024/1280/1440px와 확대 200%, 긴 한글·영문·이모지로 검사.
- 헤더는 충분한 폭에서 인라인 검색, 좁으면 동일 헤더 안 검색 모드. 입력창이 헤더 아래에 별도로 떨어지지 않는다.
- 모바일 의뢰 등록을 숨기지 않고 햄버거가 맨 오른쪽. 메뉴 내 로그인·가입, 로그인 후 로그아웃에 접근 가능.
- 호버 없는 터치, 키보드 Tab/Enter/Space/Escape 모두 동작. 드롭다운은 트리거/패널 사이 이동으로 갑자기 사라지지 않음.
- 다중 분야는 패널 유지·취소·적용·선택 칩·결과 수 일치. 모바일 시트 내부 스크롤 및 적용 버튼 접근.
- 모달/시트에 초기 포커스·포커스 범위·닫은 뒤 복귀·적절한 이름 제공. 현재 구현 여부와 별개로 운영 인수 조건이다.
- 오류는 색상만이 아닌 텍스트·필드 연결로 설명, 로딩/저장 결과는 접근 가능한 상태 메시지.
- 실사용 핵심 버튼은 44px 수준 터치 영역을 목표로 검토, 모바일 입력 16px 기준, 키보드가 CTA를 가리지 않도록 safe-area/visual viewport 검증.
- 대표 이미지 alt, 이미지 실패 fallback, 로딩 skeleton, 빈 목록, 권한 없음, 삭제된 콘텐츠 상태를 디자인 시안에 포함.
- 회귀 테스트 범위: 로그인 헤더, 필터 위치, 분야 다중선택, 예산, 의뢰 폼, 지원 대표작, 워크룸, 새 API 실패 상태.

## 6. 성능·운영 목표 초안

수치는 측정 전 제안이며 서비스 보장값이 아니다.

- 스테이징 기준 읽기 API p95 500ms, 일반 쓰기 p95 1s, 메시지 저장 후 상대 수신 p95 2s를 초기 목표로 설정하고 데이터량/동시 사용자 조건과 함께 측정.
- 이미지 크기 변형·지연 로딩·페이지 제한, N+1 조회 검출, 필터 인덱스 실행 계획 확인.
- 계약 PDF·메일·파일 검사는 HTTP 요청에서 대기하지 않고 job status로 표현.
- 테스트 데이터 규모/동시 사용자 목표는 D-03에서 합의. 숫자가 없는 ‘고성능’ 승인 금지.
- CI: frontend build/unit/E2E, backend unit/integration, DB migration, OpenAPI schema 및 consumer contract, 보안 정적 검사/의존성 검사.
- 출시 전 HTTPS·쿠키·CSRF·CORS·비밀 관리, 계정별 분리, 관리자 MFA 검토, 백업 복구·장애 연락망 확인.

이 결정 목록은 구현 중 임의로 ‘확정’으로 바꾸지 않는다. 승인 날짜·결정자·선택·근거·영향을 해당 행 또는 ADR에 남긴다.

## 8. 포트폴리오 시안 전달 체크리스트

화면을 대신 설계하지 않고 다음 질문에 답할 수 있는 시안을 요청한다: 새 작성/수정/임시저장 상태, 필수 항목, 미디어 추가·삭제·정렬, 대표 이미지, 모바일 미리보기, 공개/비공개, 업로드 중/실패, 공개 승인 대상 변경, 이탈 시 처리. 데이터 구조 변경이 있으면 PortfolioVersion·첨부·지원 스냅샷·공개 승인 API에 미치는 영향을 함께 검토한다.
