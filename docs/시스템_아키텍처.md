# 전체 시스템 아키텍처

기준일: 2026-09-30 · 상태: **목표 아키텍처 제안 / 백엔드 미구현**

## 1. 현재와 목표의 경계

현재는 React SPA가 seed 데이터 및 브라우저 저장소를 직접 읽는다. 로그인도 브라우저 데모다. 이 문서는 실제 다중 사용자 서비스를 만들기 위한 설계이며, 서버·DB·클라우드를 생성했다는 의미가 아니다.

권장 시작 구조는 **모듈형 단일 백엔드 + 관계형 DB + 비공개 객체 저장소 + 비동기 작업자**다. 초기부터 마이크로서비스·별도 검색 클러스터를 운영하지 않는다. 선정·계약·완료처럼 원자성이 필요한 작업을 하나의 DB 트랜잭션으로 묶기 쉽고, 소규모 팀이 배포·장애 대응하기 적합하다는 프로젝트 판단이다.

```text
PC / Tablet / Mobile Browser
          │ HTTPS (동일 origin 권장)
     Reverse proxy / TLS / 정적 자산 CDN
          ├─ /             React SPA
          ├─ /api/v1/*     모듈형 API 서버 ── PostgreSQL
          └─ /events      인증된 이벤트 스트림     │
                                │                 └─ Outbox / Job
                                ├─ 비공개 객체 저장소  ↔ 비동기 Worker
                                └─ 메일 어댑터          ├─ 알림·메일
                                                       ├─ 파일 검사·썸네일
                                                       └─ 계약 PDF
학교 인증 제공자(미정) ↔ 인증 어댑터
```

API와 Worker는 같은 저장소/도메인 코드 기반으로 시작하되 별도 프로세스로 실행할 수 있다. 단일 서버에서도 작업 실패가 HTTP 요청 전체를 막지 않도록 작업 테이블과 재시도를 둔다.

## 2. 기술 선택과 미확정 사항

| 계층 | 제안 | 근거 / 결정 조건 |
| --- | --- | --- |
| 프론트 | 현재 React/Vite 유지 | 기존 화면 재사용. 서버 상태와 화면 임시 상태를 분리 |
| API | REST, 모듈형 단일 앱 | 팀이 Java에 익숙하면 Spring Boot, TS에 익숙하면 NestJS 후보. **언어/버전 미확정** |
| API 문서 | OpenAPI 3.1 계약 | DTO·오류·권한·예시를 함께 관리. 프레임워크별 지원 확인 후 도구 선정 |
| DB | PostgreSQL 제안 | 관계·유일성·트랜잭션·검색 메타데이터 관리 |
| 세션 | 서버 보관 opaque session + 쿠키 | 클라이언트가 사용자 ID를 제시하는 현재 방식을 폐기 |
| 파일 | S3 호환 비공개 객체 저장소 | 파일 바이너리를 DB/localStorage에 저장하지 않음 |
| 채팅 | POST 전송 + SSE 수신을 초기안으로 | DB 저장 후 수신 이벤트. 양방향 타이핑/접속 상태 요구가 커지면 WebSocket 검토 |
| 작업 큐 | DB Job/Outbox로 시작 | 멀티 인스턴스 규모에서 Redis/브로커 도입 여부 결정 |
| 검색 | DB 필터·인덱스로 시작 | 한글/영문 혼합 검색 품질·부하 측정 후 별도 검색 엔진 검토 |
| 배포 | dev / staging / production 분리 | 사업자·리전·비용은 미확정. 비밀 관리와 백업 포함 |

OpenAPI는 명세 계약 형식으로 사용하며 모든 응답 필드를 이 문서의 요약 표만으로 구현하지 않는다. 정식 schema 작성은 백엔드 첫 단계다. [OpenAPI 3.1.1 명세](https://spec.openapis.org/oas/v3.1.1.html)

## 3. 모듈 책임

| 모듈 | 소유 데이터와 책임 | 금지 사항 |
| --- | --- | --- |
| Identity | 계정, 세션, 이메일 검증, 재설정, 약관 동의 | 프로필/요청 body에서 권한을 신뢰하지 않음 |
| Verification | 학교 인증 요청·심사·만료·철회 | 이메일 가입만으로 학교 배지 부여 금지 |
| Profile / Taxonomy | 공개 프로필, 경력, 제공 작업, 분야·기술 사전 | 계정 이메일 등 비공개 데이터와 공개 DTO 분리 |
| Portfolio | 콘텐츠, 공개 상태, 대표작, 버전, 공개 승인 | 편집기 화면은 디자인 대기, API 계약도 확정 전 협의 |
| Project / Matching | 공고, 초안, 지원, 지정 요청, 선정 | 여러 수행자 동시 선정/본인 지원 방지 |
| Collaboration | 대화방, 참여자, 메시지, 읽음, 워크룸 | 방 ID를 아는 것만으로 조회 허용 금지 |
| Contract / Delivery | 계약 버전·동의·완료 요청·후기 | 클라이언트의 SIGNED/COMPLETED 직접 지정 금지 |
| Media | 업로드 허가, 검사, 접근 URL, 폐기 | 임의 object key 소유권 인정 금지 |
| Notification | 수신자별 알림, 메일, 중복 방지 | 발송 실패로 업무 트랜잭션 취소하지 않음 |
| Operations | 신고·문의·콘텐츠 제재·감사 | 관리자 무제한 사적 메시지 열람 금지 |

모듈 간 변경은 도메인 서비스를 통해 수행한다. 동일 DB를 사용해도 서로의 테이블을 임의 수정하는 컨트롤러를 만들지 않는다.

## 4. 프론트 연동 구조

목표 디렉터리 제안: `frontend/src/api/`(HTTP·DTO), `frontend/src/features/`(기능별 서버 상태), `frontend/src/components/`(공용 UI). 지금 파일들을 한 번에 재작성하지 않고 기능 단위로 옮긴다.

- 조회/변경은 API 계층을 통해서만 수행. `frontend/src/data.js` seed는 명시적 demo 모드에서만 사용한다.
- 인증 초기화는 `GET /auth/session`. 로딩 중에는 비회원 메뉴를 순간 노출하지 않고 안정된 로딩 상태를 둔다.
- 화면 임시값(필터 초안, 열린 패널)과 서버의 확정 상태를 분리한다.
- mutation 성공 후 목록·상세·MY·알림의 관련 캐시를 갱신한다. 실패한 요청을 성공 UI로 표시하지 않는다.
- 검색 변경 시 이전 요청 취소 또는 request sequence 비교로 늦게 온 응답이 새 결과를 덮지 못하게 한다.
- 로그아웃 시 사용자별 캐시·메시지 스트림·민감한 폼 초안을 정리한다. 다른 계정 로그인 시 이전 찜/계약/방이 보이면 안 된다.
- API 장애 때 localStorage demo로 자동 fallback 하지 않는다. 명시적 재시도와 오류 상태를 보여준다.
- 현재 `field=[분야명,세부분야명]` URL은 프론트 호환 파서에서 표준 ID로 변환한다. 브라우저 공유 URL과 API 쿼리 형식이 같아야 하는 것은 아니다.

## 5. 인증·학교 인증·권한

### 인증 흐름

1. 가입: 이메일 정규화·중복 처리·서버 비밀번호 검증·필수 약관 버전 저장. 비밀번호 파생은 검증된 서버 라이브러리 사용, 알고리즘/비용은 보안 검토로 결정한다.
2. 이메일 확인: 짧은 수명, 일회용, 원문 대신 토큰 해시 저장. 회원 존재 여부를 과도하게 노출하지 않는 응답과 발송 제한.
3. 로그인: 속도 제한, 실패 처리, 세션 ID 회전. 브라우저에는 `HttpOnly; Secure; SameSite=Lax; Path=/` 쿠키 제안, Domain 미설정 및 `__Host-` 접두어 검토.
4. 요청: 서버 세션에서 사용자 ID·정지 상태를 확인하고 객체별 소유권/참여 권한을 추가 검사.
5. 로그아웃/비밀번호 변경/정지: 해당 세션 또는 전체 세션 폐기. 쿠키만 지우고 서버 세션을 남기지 않는다.
6. 재설정: 일반화된 안내 → 메일 토큰 → 유효성 확인 → 새 비밀번호 → 세션 폐기. 로그·URL 분석 도구에 토큰이 남지 않게 하고 일회성 사용은 원자적으로 처리.

세션 쿠키는 HTTPS와 수명·회전·폐기 정책을 함께 설계해야 한다. HttpOnly는 CSRF 방어를 대신하지 않는다. 상태 변경 요청은 CSRF 토큰과 Origin 검증을 적용하고 CORS는 허용 origin만 지정한다. [OWASP 세션 가이드](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

### 학교 인증

- 검증 수단은 학교 SSO 우선 검토, 학교 이메일 확인 또는 증빙 심사를 대안으로 둔다. 실제 허용 도메인·SSO 계약·학생/교직원 구분 기준은 학교 확인 전 미정.
- `UNVERIFIED → PENDING → VERIFIED / REJECTED`, 이후 `EXPIRED / REVOKED`. 반려 후 보완 재신청 가능.
- 인증 상태·종류·만료 시각은 서버가 관리하고 공개에는 배지 수준만 반환한다. 학번·직번·증빙 원본은 공개 금지.
- 운영 제안: 열람은 비회원 허용, 가입 회원은 초안/프로필 준비 가능, 게시·지원·지정 요청·새 대화는 유효 학교 인증 후 허용. 실제 학교 정책 승인 필요.
- 인증 만료가 진행 중 계약을 자동 무효화하지 않는다. 신규 거래는 제한하되 기존 거래 이행 접근은 별도 정책으로 유지한다. 정지/분쟁 상황은 운영자가 제한 범위와 사유를 기록한다.

### 객체 권한

프로젝트 소유자, 지원서 작성자, 지정 요청 당사자, 대화방 멤버, 계약 당사자 관계로 검사한다. 하나의 전역 `EXPERT` 역할로 거래 권한을 부여하지 않는다. 관리자도 문의/신고 처리 범위의 최소 권한을 사용하며 민감한 열람에 사유·감사로그를 남긴다.

## 6. 파일 처리

1. 업로드 요청에서 목적·파일명·크기·형식·연결 대상을 검사하고 서버가 임의 object key를 발급.
2. 만료가 짧은 업로드 URL로 비공개 격리 영역에 업로드.
3. 완료 요청 후 서버가 실제 객체 크기·내용 형식·소유권을 재확인하고 악성 파일 검사·이미지 재인코딩/메타데이터 제거 수행.
4. `READY`가 되기 전 공개/메시지 첨부 불가. 실패는 이유와 재업로드 동작 제공.
5. 다운로드 시 매번 대상 접근 권한 확인 후 짧은 유효기간의 URL 발급. 공개 포트폴리오에는 승인된 파생 이미지 정도만 CDN 배포.
6. 연결되지 않은 업로드·실패 파일은 정리 Job으로 제거. 공개 취소 시 CDN 및 파생본도 제거/무효화.

초기 운영 제한 제안: 이미지 10MB, PDF 20MB, 워크룸 허용 문서 20MB, 연결 대상당 10개. 영상은 우선 외부 링크, 직접 업로드·압축파일은 검사 체계와 비용 승인 후. 이는 현재 데모의 2MB/3MB 제한과 별개이며 확정값이 아니다.

확장자뿐 아니라 내용 검사, 허용 목록, 크기 제한, 안전한 파일명·저장 위치를 함께 적용한다. 외부 링크 미리보기는 초기에는 서버 fetch를 하지 않고 일반 링크로 표시하여 SSRF 경로를 줄인다. [OWASP 파일 업로드 가이드](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

## 7. 업무 트랜잭션·이벤트

- 지원/선정/계약 동의/완료는 DB 커밋이 성공한 뒤 성공 응답.
- 선정: 프로젝트 행 잠금 또는 버전 비교, 지원 유효성 검사, 유일한 선정·워크룸 생성, 기타 지원 처리, outbox 삽입을 한 트랜잭션으로 수행.
- 계약 동의: 현재 버전·본문 해시·행위자 검사와 두 동의 집계를 원자적으로 처리. 오래된 버전은 409.
- 알림·메일·PDF는 Outbox/Job을 통해 이후 처리. 재시도되어도 중복 메시지·메일·문서를 만들지 않도록 이벤트 키 사용.
- 잠금 순서를 일관되게 하고 deadlock/serialization 오류는 제한된 횟수로 재시도한다. DB 행 잠금은 다른 트랜잭션의 동시 수정을 제어하는 수단이다. [PostgreSQL 행 잠금 문서](https://www.postgresql.org/docs/17/explicit-locking.html)

## 8. 실시간 통신

- SSE 초기안: 사용자별 인증된 스트림 한 개, 서버가 참여 중인 대화방/알림 이벤트만 전송. GET 연결에는 세션 쿠키·Origin 검증.
- 메시지 전송은 POST와 `clientMessageId`를 사용. 서버가 저장한 ID·방 내부 sequence·createdAt을 응답한 뒤 전송 완료 표시.
- 재연결 시 마지막 이벤트 ID를 전달하되, 이벤트 보존 범위를 벗어나면 REST로 메시지를 재조회한다. 스트림 자체를 영구 저장소로 보지 않는다.
- 로그아웃·정지·참여 권한 변경 시 기존 연결도 종료/재검증한다. heartbeat, 프록시 buffering/timeout, 사용자별 연결 수 제한을 운영 설정에 포함.
- 이미 저장된 메시지를 전송 실패로 오인해 중복 전송하지 않도록 클라이언트 ID 유일성을 적용. 읽음은 `lastReadSequence`의 단조 증가로 관리한다.

## 9. 배포·운영·개인정보

- SPA 라우팅 fallback과 API 404를 분리한다. `/api/*` 오류가 index.html로 반환되면 안 된다.
- 로컬 dev는 개발용 DB/메일함/객체 저장소만 사용. 운영 데이터 복제 금지, 스테이징 테스트 데이터는 합성 데이터 사용.
- DB migration 버전 관리, expand/contract 배포, 롤백 시 호환되는 이전 앱 준비. 삭제 컬럼 복구를 앱 롤백으로 대신하지 않음.
- 구조화 로그에는 requestId·행위·대상 ID·지연·결과를 넣되 비밀번호·세션·재설정 토큰·채팅 원문·계약 전문·학번은 제외.
- 모니터링: API 오류율/지연, DB 연결·잠금, Outbox 적체, 메일 실패, 미검사 파일, SSE 연결 수, 객체 저장량. 알림 수신 담당자 필요.
